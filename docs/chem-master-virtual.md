# Виртуальный Химмастер 4000

Это офлайн-стенд приготовления **растворов с возвратом в буфер**. Он не нажимает в игре, не читает её память и не посылает BUI-сообщения. В тестовой сборке нет даже `Program.cs` и ClrMD; отдельно проверяется настоящий CLI с запрещённым поиском процессов.

## Запуск

Из корня репозитория:

```powershell
.\test-chemistry-virtual.ps1
.\run.ps1 --chemistry-simulate .\tests\scenarios\medicine-cycle.json
.\run.ps1 --chemistry-simulate .\tests\scenarios\small-beaker.json --json
.\run.ps1 --chemistry-simulate .\tests\scenarios\missing-ingredient.json --json
```

После запуска локальные отчёты создаются в `.test-results`. Эта папка не хранится в Git. Нужен установленный .NET 10 / ранее сохранённый `dist/dotnet-path.txt`, но не запущенная игра. Компилятор и зависимости после первоначальной сборки берутся из `.tools`.

Код выхода симулятора: `0` — все задания завершены; `4` — ожидаемая остановка модели (например, нехватка исходника); `2` — ошибочные аргументы CLI; `1` — ошибка чтения/формата/инфраструктуры. Первый заблокированный job останавливает всю очередь.

## Формат сценария

См. `tests/scenarios/medicine-cycle.json`. `buffer` — упорядоченный массив `{prototype, amount}` в игровых единицах. ID чувствителен к регистру; повторяющиеся ID отвергаются, поскольку разные `ReagentData` модель не различает. Нулевые строки не создаются, отрицательные объёмы и точность мельче 0.01u запрещены. `calibration` разрешается относительно JSON сценария; пользовательский `chemmaster-input.json` только читается.

- `jobs[].request`: тот же синтаксис названий, ID и `@категорий`, что в планировщике.
- `jobs[].mode = "ensure"` (по умолчанию): довести запас каждой цели до указанного минимума. Повтор без изменений ничего не производит.
- `mode = "make"`: добавить указанное количество сверх текущего запаса. Из-за целых партий результат может быть немного больше.
- Цели резервируются совместно **в пределах одного задания**. Предыдущие задания не становятся постоянными неснижаемыми запасами: если их нужно сохранить, включите их в следующий request.
- `beakerCapacity`: вместимость входа; `beaker`: начальное содержимое. При непустом входе приготовление блокируется, чтобы не смешать неизвестные остатки.
- `sorting`: `none`, `alphabetical`, `quantity`, `latest`; `powered` и `hasBeaker` задают виртуальные условия доступности.

Результат JSON содержит план, исходный/конечный буфер и каждый принятый шаг: ID, дозировку, текущий индекс строки, необходимость виртуальной прокрутки, точку из калибровки, реально перенесённый объём, состав после действия, температуру и сработавшие реакции. Неудачные пробные последовательности не выдаются как действия для исполнения.

## Что исправлено в приготовлении

Сначала план строится с учётом готовых лекарств и промежуточных реагентов. Во виртуальном режиме недостающие количества округляются до целых стехиометрических партий, выражаемых кнопками. Например, 5u диловена требуют по 1⅔u трёх исходников; стенд готовит 6u из 2+2+2, а лишнее возвращает. Старые `--chemistry-plan` и `--chemistry-check` сохраняют прежнюю семантику теоретического производства нового количества.

Затем **весь job** проверяется на копии состояния. Рецепт плана сравнивается с игровыми коэффициентами. Каждая кнопочная доза пропускается через все импортированные реакции, упорядоченные по приоритету, количеству продуктов и ID. Учитываются сотые доли, катализаторы, quantized, границы температур и изменение температуры через теплоёмкости. Больше вместимости — дробление на партии, а не потеря раствора.

Найденный контрпример: смешивание 4u кислорода, 4u сахара и последующая подача углерода по 1u не гарантирует 12u инапровалина. После первой порции появившийся инапровалин конкурирует за следующий углерод и образует бикаридин. Стенд перебирает порядок ингредиентов и меньшие кнопочные партии; исполняется только последовательность с проверенным конечным составом. Поиск ограничен 120 порядками на размер партии и 10000 действиями на job, поэтому отказ не доказывает, что рецепт принципиально невозможен.

См. [движок реакций](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Content.Shared/Chemistry/Reaction/ChemicalReactionSystem.cs), [приоритеты](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Content.Shared/Chemistry/Reaction/ReactionPrototype.cs), [рецепты препаратов](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Resources/Prototypes/Recipes/Reactions/medicine.yml).

После партии все строки входа возвращаются через их текущие ID. Следующий job заново строится по пополненному буферу. Во время исполнения сравнивается отпечаток **полного состава и порядка обеих ёмкостей**, режима, доступности, сортировки и температуры, а не только общего объёма. Несовпадение останавливает цепочку; уже совершённые действия не «откатываются», потерянное подтверждение не означает повторный клик.

## Что ещё НЕ доказано

- Проверка разметки структурная. Измеренный шаг строк около 26.15px во входе и 24.77px в буфере — ручные отметки могут накапливать ошибку на дальних строках. Нужно будет проверить попадание и фактическую прокрутку на живом UI. Файл разметки не исправлялся автоматически.
- Виртуальные строки имеют источник `virtual-model`. Они намеренно не допускаются в функцию привязки живого UI (`live-ui-controls`). Для настоящей игры нужна повторная проверка окна, масштаба, вкладки, scroll offset, точных ReagentId и свежего результата каждого клика.
- Модель импортирует 345 реакций и 453 вещества из 51 файла в каталогах `Recipes/Reactions` и `Reagents`, а не запускает ECS SS14. Произвольные встроенные в другие YAML прототипы, серверные модификации, события отмены реакций, окружающий теплообмен, `ReagentData`, разливы и задержки сети не воспроизведены. Катализаторы планируются консервативно по количеству рецепта, хотя для неquantized-реакции достаточно ненулевого присутствия.
- Газовые/взрывные/прочие эффекты не исполняются: подходящая реакция с эффектом блокирует сценарий. Внешний нагрев и специализированные устройства не автоматизированы. Отказ на копии не меняет начальный виртуальный запас.
- Алфавитный порядок стенда использует ru-RU и имена из каталога вики, а для неизвестных каталогу имён — ID. Это не источник точного алфавитного порядка живого клиента; там используется reader реальных UI-кнопок.
- Фасовка таблеток/бутылок не реализована. В игре она берёт смесь из выбранного источника, а не препарат выбранной строки. **Нельзя фасовать чистое лекарство из общего многокомпонентного буфера**: нужен отдельный чистый раствор и явная проверка источника выдачи.

## Обновление снимка правил

Обычный прогон не использует сеть. Для намеренного обновления — поменять зафиксированный commit в `scripts/import-game-chemistry.cjs`, установить парсер и запустить импорт:

```powershell
npm install --prefix .tools/chemistry-import yaml@2.8.1 --ignore-scripts --no-audit --no-fund
node scripts/import-game-chemistry.cjs
.\test-chemistry-virtual.ps1
```

Импорт отвергает неполное GitHub tree, дублирующиеся определения и неподдержанное наследование. Для исходных YAML записаны SHA-256 нормализованного текста (LF и одна завершающая новая строка), а не побайтовые хеши HTTP-ответа. Изменение правил требует пересмотра ожидаемых результатов; успешный старый тест не является разрешением автоматически применять новую версию к игре.

`node scripts/import-game-chemistry.cjs --verify-known-files` повторно читает известные 51 файл без GitHub tree API и работает только для того же commit. Это полезно при лимите API, но не подходит для поиска новых файлов в другой версии.
